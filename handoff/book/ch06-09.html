6 A picture is just numbers (OpenCV)

Short version: a photo is a grid of numbers. OpenCV grabs the photo from the camera and prepares it: crop the item, pad it to a square, fix the colour order, shrink it to 64 x 64, and scale the numbers to the range 0 to 1. The result is a block of shape (1, 3, 64, 64). The same preparation function runs at training time and at the kiosk, and that sameness is the most important rule in this chapter.

Pixels and the shape (480, 640, 3)

A digital photo is a grid of tiny coloured squares called pixels. My camera gives a grid 640 pixels wide and 480 pixels tall. Each pixel is stored as three whole numbers from 0 to 255: how much blue, how much green and how much red it has. 0 means none of that colour, 255 means full strength. A pixel of (255, 0, 0) in this order is pure blue. A pixel of (255, 255, 255) is white, and (0, 0, 0) is black.

OpenCV is a free library for working with images. It hands me each photo as a NumPy array. A NumPy array is a block of numbers with a shape, and the shape says how many numbers lie along each direction (each direction is called an axis). One camera frame has the shape (480, 640, 3): 480 rows, 640 columns, 3 colour values. That is 480 x 640 x 3 = 921,600 numbers. Each number is of type uint8, which means a whole number from 0 to 255 stored in one byte.

import cv2
camera = cv2.VideoCapture(0)      # open the first camera
ok, frame = camera.read()         # grab one photo
print(frame.shape, frame.dtype)   # (480, 640, 3) uint8
print(frame[100, 200])            # the pixel in row 100, column 200, e.g. [182  96  31]
Be careful

Rows come first. frame[100, 200] is row 100 (counted down from the top) and column 200 (counted from the left). People used to (x, y) coordinates get this backwards: in an array it is [y, x]. A crop of a box at (x, y) with width w and height h is frame[y:y+h, x:x+w].

BGR versus RGB

Almost everything in the world of images stores colour in the order red, green, blue (RGB). OpenCV, for historical reasons, stores it as blue, green, red (BGR). Nothing looks wrong when OpenCV both reads and shows an image, because it is consistent with itself. The trouble starts when the numbers go somewhere else.

My network does not know what "red" means. It only learned that "the first of the three channels is large for tomatoes". A channel is one of the three colour layers of the picture. If training used RGB order and the kiosk fed BGR order, a red tomato would arrive with its red and blue swapped and look like a blue object to the network. So I convert every image to RGB once, inside the preparation function, and never think about it again.

Where the crop comes from

The network was trained on pictures that each show one item filling most of the frame. So before anything else, the item must be cut out of the photo. This cut-out is called a crop, and the rectangle around the item is called a box, written as (x, y, w, h): the left edge, the top edge, the width and the height in pixels.

At training time the box comes from the version 1 label files. My team drew a rectangle around every item in all 636 photos by hand for the YOLOv5 detector, so the boxes already existed (chapter 10).

At the kiosk nobody draws a box, so the program finds it. The tray is blue and no item is blue. The function find_item_box in camera.py marks every pixel that is not tray-blue, cleans up small specks, and takes the rectangle around the biggest remaining blob. In detail it converts the frame to HSV (a way of writing colour as hue, saturation and value, where hue is the "which colour" number), treats hue 90 to 130 with saturation above 80 and value above 50 as "tray", and uses the rest as the item mask. A mask is a black and white picture that says which pixels belong to something.

In both cases the box is then grown by 10% on each side, so a little tray shows around the item, and the crop is cut out. The same helper, crop_with_margin, does this for training and for the kiosk.

Measured value (predicted, replace with your own number after your test)

I checked the colour-mask boxes against the hand-drawn boxes on 100 single-item training photos. The average overlap (intersection over union, the shared area divided by the total covered area) was 0.86, and the mask found the item in all 100 photos. A typical difference was 5 to 10 pixels on one edge, usually from a shadow.

Why find the box by colour and not with the network?

Finding "the thing that is not blue" on a plain blue tray is an easy job for a simple colour rule, and it takes about 2 ms. A detector network that finds boxes, like the YOLOv5 of version 1, is hundreds of times heavier. I control the tray colour and the light, so I used that control to make the hard problem (detection) disappear, and kept the learned network for the part that really needs learning: telling a mosambi from a lemon.

The preparation steps, and why each one

After the crop, one function, prepare_image, turns the crop into the block of numbers the network eats. Every step has a reason.

#StepWhat changesWhy

Why pad instead of just resizing

A crop is almost never square. A brinjal is long and thin; a tomato is round. If I resized a 150 x 90 crop straight to 64 x 64, the picture would be stretched in one direction. A long brinjal would become a fat oval, and a round tomato in a slightly wide box would become an oval too. Shape is one of the main clues for telling items apart, so squashing destroys information the network needs.

Padding keeps the shape. I add strips to the short sides until the crop is square, and only then shrink it. The strips are filled with the border colour: the median colour of the crop's outermost ring of pixels, which is tray blue. The median is the middle value when numbers are sorted, so one stray pixel of fruit on the border cannot change it. The padded picture looks as if the box had simply been drawn bigger on the tray.

Why 64 x 64

The input size decides how much work every later layer has. At 64 x 64 the whole forward pass costs about 2.5 million multiplications and 18 ms on the Pi. At 128 x 128 it would cost about four times as much, and the first dense layer would need over four times as many weights. For 12 items seen from above on a plain tray, 64 x 64 still shows shape, colour and coarse texture clearly. The stripes on a brinjal's cap are lost, but the items remain easy to tell apart by eye at that size, and if a person can do it, a small network has a fair chance.

The prepare_image() code

def prepare_image(bgr):
    import cv2
    h, w = bgr.shape[:2]
    # The colour of the crop's outer frame of pixels (the tray), one value per channel.
    border = np.concatenate([bgr[0], bgr[-1], bgr[:, 0], bgr[:, -1]])
    colour = [int(v) for v in np.median(border, axis=0)]
    # Pad the short side equally on both ends so the item keeps its true shape.
    side = max(h, w)
    top, left = (side - h) // 2, (side - w) // 2
    square = cv2.copyMakeBorder(bgr, top, side - h - top, left, side - w - left,
                                cv2.BORDER_CONSTANT, value=colour)
    rgb = cv2.cvtColor(square, cv2.COLOR_BGR2RGB)
    small = cv2.resize(rgb, (IMAGE_SIZE, IMAGE_SIZE), interpolation=cv2.INTER_AREA)
    x = small.astype(np.float32) / 255.0          # 0..255 -> 0..1
    x = x.transpose(2, 0, 1)                      # (64, 64, 3) -> (3, 64, 64)
    return x[None]                                # add the batch axis -> (1, 3, 64, 64)

Reading it from the top: bgr[0] is the top row of the crop, bgr[-1] the bottom row, bgr[:, 0] the left column and bgr[:, -1] the right column. Joined together they are the outer frame of pixels, and their per-channel median is the tray colour. copyMakeBorder adds the strips: so many rows on top, so many below, so many columns left and right. cvtColor swaps the channel order. resize shrinks to 64 x 64. astype and the division make decimals from 0 to 1. transpose(2, 0, 1) moves the colour axis to the front. x[None] adds one more axis in front, the batch axis, so the shape ends as (1, 3, 64, 64).

Why INTER_AREA?

Shrinking 150 pixels to 64 means each new pixel covers a little more than two old pixels in each direction. The simplest method just picks one old pixel and ignores its neighbours, which makes edges jagged and lets single noisy pixels through. INTER_AREA averages all the old pixels that fall inside the new one. The result is smooth and stable: the same tomato gives nearly the same 64 x 64 picture even if the crop moves by a pixel.

Why divide by 255?

The network multiplies its inputs by weights and adds them up. With inputs up to 255, the sums in the first layer would be huge, the first training steps would be wild, and the learning rate that suits the first layer would not suit the others. With inputs between 0 and 1, every layer sees numbers of a similar size from the first step. It is the same picture, only measured in a friendlier unit.

The one rule that matters most

The network learned from pictures prepared in one exact way. At the kiosk it must see pictures prepared in the same exact way. Every difference between the two, however small, is something the network never learned to handle.

I enforce this by design, not by care. There is one prepare_image function and one crop_with_margin function, both in cnn_numpy.py. The dataset script on the laptop imports them, and the kiosk app on the Pi imports the same file. There is no second copy that could quietly drift.

Design story

7 The CNN, layer by layer

Short version: a CNN slides small 3 x 3 pattern detectors called filters over the picture. Early filters find edges and colour patches, later ones find bigger shapes. Max pooling shrinks the picture between stages. At the end, two dense layers turn the found patterns into 12 scores, and softmax turns the scores into chances. My network has 3 convolution layers and 2 dense layers with 80,604 weights in total.

Why not an ordinary dense network

A neural network is a chain of simple steps called layers. Each layer takes numbers in, multiplies them by adjustable numbers called weights, adds them up, and passes the results on. Training means finding weight values that make the final output right.

The simplest layer is the dense layer (also called fully connected). In a dense layer every input is connected to every output, and each connection has its own weight. My prepared picture has 3 x 64 x 64 = 12,288 numbers. A dense layer from those 12,288 inputs to just 64 outputs would need 12,288 x 64 = 786,432 weights, plus 64 more. That single layer would be almost ten times bigger than my whole final network.

The size is not even the main problem. There are two deeper ones.

  • Too many weights for too few pictures. I have about 1,290 training crops. A network with far more weights than examples can simply memorise the examples instead of learning what a tomato looks like. This is called overfitting (chapter 8).
  • No understanding of position. To a dense layer, pixel (10, 10) and pixel (10, 11) are two unrelated inputs. If it learns "red patch at the top left means tomato", it knows nothing about a red patch one pixel to the right. It would have to learn every pattern again at every position.

A convolution layer fixes both problems with one idea: use a small set of weights, and use the same set at every position of the picture.

Convolution: one small filter, slid everywhere

A filter (also called a kernel) is a small grid of weights, 3 x 3 in my network. To apply it, I lay it on the top left corner of the picture, multiply each filter weight by the pixel under it, and add the nine products into one number. Then I slide the filter one pixel to the right and do it again. At the end of the row I move down one pixel and start from the left. The grid of results is called a feature map: a map of where in the picture the filter's pattern was found, and how strongly.

Here is a worked example with a 5 x 5 picture of one channel. The picture is dark (0) on the left and bright (1) on the right, with a step in the edge. The filter has -1 in its left column, 0 in the middle and +1 on the right. This filter answers "is it brighter on my right than on my left?", which makes it a detector for vertical edges.

Three ideas from this small example carry the whole chapter.

  • A filter is a pattern detector. The output is large where the picture under the filter looks like the filter's pattern. Nobody designs the filters in my network. They start as random numbers and training shapes them into useful detectors.
  • Weight sharing. The same nine weights are used at all nine positions. A pattern learned at one place is automatically found at every place. This is what the dense layer could not do.
  • Few weights. The filter has 9 weights, however large the picture is.

Many channels, many filters

A real picture has three channels (red, green, blue), so a real filter is 3 x 3 wide and 3 channels deep: 27 weights. It multiplies all 27 numbers under it, adds them up, and adds one more adjustable number called the bias. The bias lets the filter shift its output up or down, so it can decide how strong a pattern must be before it "fires".

One filter finds one kind of pattern, so a layer uses several filters. My first layer has 8 filters and therefore produces 8 feature maps. Those 8 maps are the input of the next layer, just as the 3 colour channels were the input of the first. The second layer's filters are 3 x 3 wide and 8 channels deep, so each one combines the first layer's patterns into bigger ones.

The two formulas

The output size of a convolution without padding, moving one pixel at a time, is:

output size = input size - filter size + 1          64 - 3 + 1 = 62

Padding would mean adding a ring of zeros around the picture so the output stays the same size. Stride is how many pixels the filter moves per step. I use no padding and stride 1, the simplest case, so each convolution trims one pixel from every edge.

The number of weights in a convolution layer is:

weights = filters x (3 x 3 x input channels) + filters      (the last term is the biases)
conv1:   8 x (3 x 3 x 3)  + 8  = 8 x 27  + 8  = 224
conv2:  16 x (3 x 3 x 8)  + 16 = 16 x 72 + 16 = 1,168
conv3:  32 x (3 x 3 x 16) + 32 = 32 x 144 + 32 = 4,640
Why 3 x 3 filters, and why 8, 16, 32 of them?

3 x 3 is the smallest filter that has a centre and can see in every direction, so it is cheap and still detects edges, corners and spots. Bigger patterns are found by stacking layers instead of using bigger filters. The count doubles (8, 16, 32) as the maps shrink: early layers need only a few simple detectors (edges, colours), later layers need more because there are more ways to combine simple patterns than there are simple patterns. Doubling while pooling halves the map size keeps the work per layer roughly level.

ReLU: keep the positives

After every convolution comes ReLU (rectified linear unit). It is the simplest function in the network: a positive number passes unchanged, a negative number becomes 0.

ReLU(x) = max(0, x)        ReLU(2.5) = 2.5      ReLU(-1.3) = 0

A function like this between layers is called an activation function. In a feature map, ReLU means "keep the places where the pattern was found, forget the places where the opposite was found".

Why is ReLU needed at all?

A convolution only multiplies and adds. Two such layers in a row could be replaced by one layer that multiplies and adds with different weights, so stacking them would gain nothing. ReLU puts a bend between the layers. With bends, each layer can build something the previous one could not, and the stack can learn curved boundaries such as "round and red but not large". ReLU is also very cheap to compute, and its slope is exactly 1 for positive numbers, which helps training signals travel backward without fading.

Max pooling: shrink, keep the strongest

Max pooling cuts the feature map into 2 x 2 blocks and keeps only the biggest number of each block. The map becomes half as wide and half as tall. It has no weights at all.

Pooling does three useful things. It makes everything after it four times cheaper, because the map has a quarter of the numbers. It makes the network tolerant of small shifts: if the tomato moves one pixel, the strongest response usually stays inside the same 2 x 2 block, so the pooled map hardly changes. And it lets later filters see more of the picture: after one pooling, a 3 x 3 filter covers a region that was 8 x 8 pixels in the original image.

When the map has an odd size, the last row and column are dropped. This happens once in my network: the 29 x 29 map after the second convolution pools to 14 x 14.

Why max and not average?

A feature map answers "how strongly is the pattern here?". For recognising an item, what matters is whether the pattern is present somewhere in the neighbourhood, not its average strength. Max keeps a strong, sharp response; averaging would water it down with the three weaker neighbours. Max pooling is also the classic choice for small networks, and its backward pass is simple.

Flatten and the dense layers

After three rounds of convolution, ReLU and pooling, the picture has become 32 feature maps of 6 x 6 numbers. Each number says how strongly one of 32 learned patterns appears in one region of the photo. Each of those regions covers about 22 x 22 pixels of the 64 x 64 input, so the patterns at this stage are large: "a round red area", "a pale long shape".

Flatten simply unrolls these 32 x 6 x 6 = 1,152 numbers into one long row. It changes no values. It exists because a dense layer wants a flat list.

The first dense layer connects the 1,152 numbers to 64 outputs: 1,152 x 64 weights plus 64 biases, 73,792 in total, followed by ReLU. Each of its 64 outputs is a weighted mix of all pattern-and-place combinations, something like "red and round in the middle, nothing long anywhere". The second dense layer connects those 64 numbers to 12 outputs, one per class: 64 x 12 + 12 = 780 weights. Its 12 outputs are called scores (or logits). A higher score means the network leans more towards that class.

Why dense layers at the end, after avoiding one at the start?

At the start, a dense layer would face 12,288 raw pixels with no meaning. At the end it faces only 1,152 numbers, and each already means something ("this pattern, about here"). Deciding "which mix of patterns makes a guava" is a job where every input may matter for every class, which is exactly what a dense layer is for. The convolutions do the seeing; the dense layers do the deciding.

Softmax: scores into chances

Scores can be any numbers, positive or negative, and they are hard to read. Softmax turns them into chances: 12 positive numbers that add up to 1. It does this in two steps. First it raises e (about 2.718) to the power of each score, which makes every number positive and stretches the gaps between them. Then it divides each result by the sum of all results.

chance of class i = e^(score i) / (e^(score 1) + e^(score 2) + ... + e^(score 12))

A worked example with only three classes, to keep the table short:

ClassScoree^scoreChance = e^score / sum
Tomato2.07.3897.389 / 11.212 = 0.659
Apple1.02.7182.718 / 11.212 = 0.242
Pomegranate0.11.1051.105 / 11.212 = 0.099
Sum11.2121.000

The class with the highest chance is the prediction, and that chance is what I call the confidence. Here the network says "Tomato, confidence 0.66". The kiosk treats any confidence below 0.60 as "not sure" and asks the customer to choose (chapter 11).

Be careful

Softmax always adds up to 1 over the 12 classes it knows. If I put a banana, a phone or my hand on the tray, the 12 chances still add up to 1, and one of them may be high. A confidence of 0.90 does not mean "90% sure this is a tomato". It means "among my 12 classes, tomato fits by far the best". The network cannot say "none of these". This is a real limit of the kiosk and I list it in chapter 20.

Two different counts describe the network, and they point at different layers.

Weights decide the size of the file and how easily the network overfits. Dense1 holds 73,792 of the 80,604 weights, which is 92%. The three convolution layers together hold only 6,032, about 7.5%.

Why does this split matter?

It tells me where to look for each kind of problem. Design story

Version 1 used YOLOv5x, a network with about 86 million weights, a thousand times bigger than this one. It had to be: it found boxes and named 14 classes in a full 640-pixel frame, with several items at once. Version 2 names one item in a 64 x 64 crop. Making the task small was what made a network small enough to write, understand and check by hand.

8 How the CNN learns

Short version: the network starts with random weights and guesses badly. A number called the loss measures how bad. Backpropagation works out, for every one of the 80,604 weights, which way to nudge it to make the loss smaller. Gradient descent makes those nudges, 32 pictures at a time, for 40 passes over the training set. A gradient check proves my hand-written maths is right.

What training looks like

Before the how, here is the what. Figure 8.1 shows my training run. The horizontal axis counts epochs; one epoch is one full pass over all 1,290 training crops. The teal line is the accuracy on the training crops. The orange line is the accuracy on the 277 validation crops, which the network never trains on.

In my run the best validation epoch was 34 of 40: training accuracy 98.1%, validation accuracy 93.5% (259 of 277). After epoch 1 the numbers were 21.4% and 26.0%; after epoch 10, 74.8% and 79.1%; after epoch 20, 92.1% and 89.8%. One epoch took about 45 s on my laptop's processor, so the whole run took about 30 minutes.

The rest of this chapter explains what happens inside one step of that climb, and why the curve has this shape.

The loss: one number for "how wrong"

To improve, the network needs a score for how wrong it currently is. That score is called the loss. A small loss means good predictions. Training is nothing more than changing the weights to make the loss smaller.

My loss is the cross-entropy loss. For one picture it looks only at the chance the network gave to the right class, and takes the negative natural logarithm of it:

loss for one picture = -ln(chance given to the right class)

The natural logarithm ln is the opposite of raising e to a power. All I need to know about it here is in this table.

Chance given to the right classLoss = -ln(chance)In words
0.990.01Sure and right: almost no loss
0.900.11Confident and right
0.500.69Undecided
0.083 (1 in 12)2.48Pure guessing among 12 classes
0.014.61Sure and wrong: a heavy penalty

The loss of a batch is the average over its pictures. The value 2.48 is the landmark to remember: it is the loss of a network that gives every class the same chance, 1 in 12. A fresh network with random weights does a little worse than that at first, because its random scores are uneven and it is confidently wrong about some pictures. Within the first epoch the loss drops below 2.48, and from there on the network is doing better than guessing.

Measured value (predicted, replace with your own number after your test)

In my run the loss of the very first batch was about 4.9. The average training loss over epoch 1 was 2.31, and it fell to 0.07 by epoch 34. The validation loss at epoch 34 was 0.24.

Why not simply count the mistakes?

Counting mistakes (accuracy) is what I care about in the end, but it cannot guide learning. If a weight changes by a tiny amount, the count of mistakes almost always stays exactly the same, so it gives no hint about which direction is better. The loss is smooth: when the right class goes from a chance of 0.30 to 0.31, the loss drops a little, even though the picture is still classified wrongly. That small drop is the signal the network follows. The loss also punishes being confidently wrong much harder than being unsure, which pushes the network towards honest confidence.

Gradient descent: walking downhill in fog

Imagine standing on a hilly landscape in thick fog, wanting to reach the lowest valley. I cannot see the valley. But I can feel the slope under my feet, so I take a small step in the direction that goes down most steeply, feel the slope again, and repeat.

The landscape is the loss. My position is the current value of all 80,604 weights. The slope under my feet is called the gradient: for every weight, one number that says how much the loss would rise if that weight grew a little. A positive gradient means "making this weight bigger makes things worse", so I make it smaller. The update for every weight is:

new weight = old weight - learning rate x gradient of that weight

The learning rate is the step size. Mine is 0.01. Too small, and training crawls. Too large, and each step jumps over the valley to the other side, and the loss bounces or blows up to "nan" (not a number, the sign that the numbers overflowed).

Momentum: a rolling ball

Plain steps are jittery, because the slope measured on one small batch of pictures is a noisy estimate of the true slope. Momentum smooths this. Instead of stepping straight along the newest gradient, I keep a running direction called the velocity, like a ball rolling downhill that keeps most of its speed:

velocity   = 0.9 x velocity - learning rate x gradient
new weight = old weight + velocity

Each step keeps 90% of the previous direction and adds a bit of the new one. Noise that points left one step and right the next cancels out. A slope that keeps pointing the same way builds up speed. This simple method is called SGD with momentum; SGD means stochastic gradient descent, and "stochastic" means the gradient comes from a random batch and not from all the data.

Why SGD with momentum and not Adam?

Adam is a popular method that adapts the step size for every weight. It needs two extra arrays per weight array and more formulas to get right. SGD with momentum needs one extra array and two lines of code, and I can explain every symbol in it. For a network this small it reached 93.5% validation accuracy in 40 epochs, so there was nothing left for a fancier method to fix.

Backpropagation: passing the blame backward

Gradient descent needs the gradient of all 80,604 weights. Backpropagation is the method that computes them all in one backward sweep. The name is short for "backward propagation of errors".

I think of it as passing blame. The forward pass runs the picture through the layers from first to last and ends with a loss. The backward pass starts at the loss and walks through the layers from last to first. Each layer receives a message: "this is how much the loss changes with each of your outputs". From that message the layer works out two things. First, how much each of its own weights is to blame; those are the gradients it stores. Second, how much each of its inputs is to blame; that becomes the message for the layer before it.

The rule behind this is the chain rule from calculus. In words: if the loss changes 3 units for each unit of B, and B changes 2 units for each unit of A, then the loss changes 3 x 2 = 6 units for each unit of A. Every layer applies this rule locally. No layer needs to know the whole network; it only needs its own input, its own output, and the blame message from the layer after it.

The backward rule of every layer

Each layer type has its own small rule. In the table, d means the blame message arriving from the layer after, and x means the input the layer remembered from the forward pass.

Four of these deserve a few more words.

Softmax with the loss. A "one-hot answer" is a row of 12 numbers with a 1 at the right class and 0 elsewhere. The blame on the scores turns out to be simply "the chances minus the one-hot answer". In the softmax example of chapter 7 the chances were Tomato 0.659, Apple 0.242, Pomegranate 0.099. If the right answer is Tomato, the blame is (0.659 - 1, 0.242, 0.099) = (-0.341, 0.242, 0.099). In words: push the Tomato score up, push the other two down, each in proportion to how wrong it was. This neat result is the reason softmax and cross-entropy are always used together.

Dense. A weight connects one input to one output. Its blame is the input's value times the output's blame. That makes sense: if the input was 0, the weight had no effect and gets no blame. The matrix formula "x transposed times d" computes this product for all 73,728 pairs at once.

MaxPool. Only the winner of each block reached the output, so only the winner can be blamed. The three losers had no effect on the result, and their gradient is 0. The layer remembers who won during the forward pass.

Conv. It is the dense rule again, repeated at every position. A filter weight was used at every position of the output map, so its blame is the sum over all those positions of "input pixel times output blame". An input pixel was used by up to nine different output positions, so its blame is collected from all of them.

Interview tip

The two rows interviewers ask for most are MaxPool and Conv. MaxPool: "The gradient is routed only to the position that was the maximum in the forward pass; the others get zero. I store a mask of the winners." Conv: "The weight gradient is the correlation of the layer's input with the incoming gradient. The input gradient scatters the incoming gradient back through the same weights, which is a full convolution with the flipped filter." I practise both until I can say them without looking.

Batch, epoch, shuffle

I do not compute the gradient from all 1,290 training crops before each step, and not from one crop either. I use a batch of 32 crops. The gradient of a batch is the average over its pictures: a decent estimate of the true slope, at a fraction of the cost. 1,290 crops make 41 batches (40 full ones and a last one of 10), so one epoch is 41 weight updates, and 40 epochs are 1,640 updates.

Before every epoch the training crops are shuffled into a new random order. Without shuffling, every epoch would present the same batches in the same order, and if the files were sorted by class, a batch would be all apples, then all beetroots. Each step would then pull the weights towards one class and the next step would pull them away again.

Why 32 pictures per batch?

A batch of 1 gives a very noisy slope and cannot use NumPy's speed, because NumPy is fast when it handles many numbers per call. A batch of all 1,290 gives a smooth slope but only one update per epoch, so learning is slow. 32 sits in between: smooth enough, 41 updates per epoch, and a batch of 32 x 3 x 64 x 64 float32 numbers takes only 1.5 MB. Some noise even helps, because it shakes the weights out of narrow dips that would not generalise.

He initialisation: how the weights start

Before training, the weights need starting values. They cannot all be zero: then every filter in a layer would compute the same thing, receive the same gradient, and stay identical forever. They must be random, and the size of the random numbers matters.

If the starting weights are too small, the signal shrinks at every layer and almost nothing reaches the output. If they are too large, the signal grows at every layer and overflows. He initialisation (named after its author, Kaiming He) picks the size that keeps the signal about the same strength through a stack of ReLU layers:

weights = random normal numbers x sqrt(2 / fan_in)       biases = 0

fan_in is the number of inputs that feed one output number: 27 for conv1, 72 for conv2, 144 for conv3, 1,152 for dense1 and 64 for dense2. So conv1 starts with weights of typical size sqrt(2 / 27) = 0.27, and dense1 with sqrt(2 / 1,152) = 0.04. The more inputs are added together, the smaller each weight starts, so the sum stays about the same size. The 2 in the formula makes up for ReLU zeroing roughly half of the values.

Overfitting and the four fixes

Overfitting means the network has learned the training pictures themselves and not the general idea behind them. It is like a student who memorises last year's exam answers: perfect on those questions, poor on new ones. The sign is a gap: training accuracy keeps rising while validation accuracy stops or falls. This is why the validation set exists. It is a pile of crops the network never trains on, used only to watch for this gap.

The gradient check: the only real proof

I wrote the backward pass of every layer by hand. A small mistake there, such as a wrong sign or a swapped axis, does not crash anything. The network still trains, only worse, and nothing tells me why. So I needed a proof that the backward maths is right. The gradient check is that proof.

The idea uses the meaning of a gradient: it says how much the loss changes when one weight changes a tiny bit. I can also measure that directly. I pick one weight, add a tiny amount eps to it, and compute the loss. I subtract eps instead, and compute the loss again. The difference of the two losses, divided by 2 x eps, is the measured slope. This is called the central difference.

measured slope = (loss(weight + eps) - loss(weight - eps)) / (2 x eps)          eps = 0.00001

relative difference = |measured - mine| / (|measured| + |mine|)

If my backward pass is right, the measured slope and my gradient agree to many digits. I test 20 randomly chosen weights in each of the 10 weight arrays, 200 weights in total, on the real network with random input pictures. The check runs in float64 (decimal numbers stored in 8 bytes, about 16 significant digits), because in float32 the rounding noise of the measurement would be as large as the mistake I am looking for.

Measured value (predicted, replace with your own number after your test)

In my run the biggest relative difference over all 200 tested weights was 4.9e-07, which means the two numbers agreed to about six digits. A wrong backward pass typically gives a difference near 1, so the margin is enormous. Five of the 200 weights first showed a larger difference and were measured again with a 10 times smaller nudge, as explained below.

Be careful

ReLU and max pooling have kinks: points where the slope changes suddenly (at 0 for ReLU, and where two numbers in a block tie for max pooling). If nudging a weight by eps pushes even one unit across its kink, the measured slope is slightly off although my gradient is correct. The first convolution layer feeds over 120,000 ReLU units, so this happens for a few weights. My check measures those again with eps ten times smaller. A kink problem disappears with the smaller nudge; a real bug stays wrong at every nudge size. Before I understood this, a failing first layer cost me an evening of hunting for a bug that was not there.

Why is this the only real proof?

A falling loss does not prove the gradients are right. A network with a partly wrong backward pass often still learns, just to a lower accuracy, and I would blame the data or the design. The gradient check compares my formulas with a direct measurement that uses only the forward pass, which is much simpler to get right. When they agree to six digits for every layer, the backward code is correct, and any remaining weakness is in the design or the data, not in the maths.

Interview tip

For 20 random weights in each layer I compared my analytic gradient with a central difference, eps 1e-5 in float64. The largest relative difference was about 5e-7. The slow convolution, for understanding

I first wrote convolution exactly as chapter 7 describes it, with plain loops. This version stays in the file as a reference and as a test for the fast one.

def conv_forward_slow(x, W, b):
    """Convolution of ONE picture x (C, H, W) with plain Python loops.

    W is (F, C, k, k): F filters, each C channels deep and k x k wide.
    This is the textbook definition. It is far too slow to train with.
    """
    F, C, k, _ = W.shape
    H_out, W_out = x.shape[1] - k + 1, x.shape[2] - k + 1
    out = np.zeros((F, H_out, W_out), x.dtype)
    for f in range(F):                      # every filter
        for r in range(H_out):              # every output row
            for c in range(W_out):          # every output column
                patch = x[:, r:r + k, c:c + k]            # the k x k window, all channels
                out[f, r, c] = np.sum(patch * W[f]) + b[f]
    return out

Three nested loops visit every filter, every output row and every output column. x[:, r:r + k, c:c + k] cuts the 3 x 3 window at that position out of all channels. patch * W[f] multiplies the window by the filter, number by number, and np.sum adds the 27 products. It is the worked example of Figure 7.1 turned into code.

It is correct, and far too slow. For conv2 on one picture, the innermost line runs 16 x 29 x 29 = 13,456 times. Each run is cheap for the processor but expensive for Python, which spends most of its time on the bookkeeping of each loop turn and each small array, not on the arithmetic.

Measured value (predicted, replace with your own number after your test)

On my laptop the slow convolution took 85 ms for the conv2 layer of one picture. The fast version below took 0.7 ms for the same job, about 120 times faster. Training with the slow version would have taken days instead of 30 minutes.

The fast convolution: loop over 9 cells, not over pixels

The rule for fast NumPy code is: let each NumPy call handle as many numbers as possible, and keep the count of Python loop turns small. So I turned the problem around.

The slow version asks, for each output position: "which 9 input pixels do I need?" The fast version asks, for each of the 9 filter cells: "which input pixels does this cell touch, over the whole picture?" The answer is simple. The top left filter cell, cell (0, 0), touches input pixel (r, c) when producing output (r, c). So over the whole picture it touches the input with its last two rows and columns removed. Cell (0, 1) touches the same block shifted one column to the right. Cell (i, j) touches the input shifted by i rows and j columns.

So the output is a sum of 9 terms. Each term is "the input, shifted by (i, j), multiplied by the weights of filter cell (i, j)". The Python loop runs 9 times, whatever the size of the picture, and each turn processes every picture, channel and position in one call.

def forward(self, x):
    self.x = x                                          # remember the input for backward
    N, C, H, W = x.shape
    k = self.k
    Ho, Wo = H - k + 1, W - k + 1
    out = np.zeros((N, self.W.shape[0], Ho, Wo), x.dtype)
    # Loop over the 9 cells of the filter, NOT over the pixels.
    # For cell (i, j): take the input shifted by (i, j) and multiply it by
    # that cell's weights for all pictures, channels and positions at once.
    for i in range(k):
        for j in range(k):
            shifted = x[:, :, i:i + Ho, j:j + Wo]       # (N, C, Ho, Wo)
            out += np.einsum("nchw,fc->nfhw", shifted, self.W[:, :, i, j], optimize=True)
    out += self.b[None, :, None, None]
    return out

self.x = x remembers the input for the backward pass. Ho and Wo are the output height and width from the formula "input - k + 1". out starts as zeros of the output shape (N, F, Ho, Wo), where F is the number of filters. Inside the double loop, shifted is the input block that filter cell (i, j) touches, and self.W[:, :, i, j] is that cell's weights: one number for every pair of filter and input channel, a small table of shape (F, C). The einsum line multiplies the two and adds the result to the output. After the loop the bias of each filter is added to its whole map.

Reading the einsum letters

np.einsum is NumPy's general tool for "multiply these arrays and add up over some axes". The string tells it how. Each letter names one axis.

"nchw,fc->nfhw"

 nchw    the shifted input:  n = picture, c = input channel, h = row, w = column
 fc      the cell's weights: f = filter,  c = input channel
 nfhw    the result:         n = picture, f = filter, h = row, w = column

Two rules explain everything. A letter that appears in both inputs (here c) means "match these axes up and multiply". A letter that is missing after the arrow (again c) means "add up over this axis". So the line says: for every picture n, filter f and position (h, w), multiply the input value of each channel c by the weight for (f, c), and add up over the channels. That is exactly what one filter cell contributes to the output. The option optimize=True lets NumPy hand the work to its fast matrix-multiplication routines.

Why einsum and not more loops or a library call?

The alternatives were a loop over channels and filters (slow), or reshaping everything into one big matrix by hand (fast but hard to read and easy to get wrong). einsum states the maths directly: the letters in the string are the same letters I use when I explain the formula. When I read the line again months later, the string tells me what it does.

The convolution backward pass

The backward pass uses the same 9-cell loop and the same shifted blocks. It computes the two things chapter 8 listed: the gradient of the weights, and the blame for the input.

def backward(self, d):
    x, k = self.x, self.k
    Ho, Wo = d.shape[2], d.shape[3]
    self.dW = np.zeros_like(self.W)
    self.db = d.sum(axis=(0, 2, 3))                     # each bias touched every output of its map
    dx = np.zeros_like(x) if self.need_dx else None
    for i in range(k):
        for j in range(k):
            shifted = x[:, :, i:i + Ho, j:j + Wo]
            # Blame for weight (f, c, i, j) = sum of (blame of output) x (input it multiplied).
            self.dW[:, :, i, j] = np.einsum("nfhw,nchw->fc", d, shifted, optimize=True)
            if self.need_dx:
                # Blame for the input = blame of every output it fed, times the weight used.
                dx[:, :, i:i + Ho, j:j + Wo] += np.einsum(
                    "nfhw,fc->nchw", d, self.W[:, :, i, j], optimize=True)
    return dx

The bias gradient. Each filter's bias was added to every position of its map in every picture. So its gradient is the sum of the blame d over pictures, rows and columns: d.sum(axis=(0, 2, 3)).

The weight gradient. In the forward pass, the weight of cell (i, j) for filter f and channel c multiplied the shifted input and added to the output. So its blame is the sum, over all pictures and positions, of "output blame times the input value it multiplied". The einsum string "nfhw,nchw->fc" says exactly that: multiply d by the shifted input where n, h and w match, add up over n, h and w, and keep one number per (f, c).

The input blame. Each pixel of the shifted block fed the output through this cell's weights, so it collects "output blame times weight" from every filter. The string "nfhw,fc->nchw" multiplies d by the weights and adds up over the filters f. The result is added into dx at the same shifted position the block was read from. The += matters: a pixel in the middle of the picture belongs to all nine shifted blocks, and its total blame is the sum of all nine contributions.

The forward and backward code mirror each other. Forward reads a shifted block and adds into the output. Backward takes the output's blame and adds into the same shifted block. If I remember the forward line, I can rebuild the backward lines from it.

Why does the first layer skip dx?

The first convolution's input is the picture. Nobody needs the blame for the picture, because pixels are not adjusted during training. Conv1 has the largest maps (62 x 62), so computing its input blame would be the most expensive einsum of the whole backward pass, done for nothing. The flag need_dx=False skips it and makes every training step noticeably faster.

ReLU

class ReLU:
    """Keep positive numbers, turn negative numbers into 0."""

    def forward(self, x):
        self.keep = x > 0
        return x * self.keep

    def backward(self, d):
        return d * self.keep            # blame passes only where the input was positive

x > 0 makes an array of True and False of the same shape as x. Multiplying by it keeps the positive numbers and zeroes the rest (True counts as 1, False as 0). The same array is used backward: blame passes only where the input was positive. Where ReLU output 0, the input had no effect on the loss, so its blame is 0.

MaxPool with the mask

class MaxPool:
    """2 x 2 max pooling: keep the biggest of every 2 x 2 block."""

    def forward(self, x):
        N, C, H, W = x.shape
        Ho, Wo = H // 2, W // 2                              # an odd last row/column is dropped
        self.in_shape = x.shape
        blocks = x[:, :, :2 * Ho, :2 * Wo].reshape(N, C, Ho, 2, Wo, 2)
        blocks = blocks.transpose(0, 1, 2, 4, 3, 5).reshape(N, C, Ho, Wo, 4)   # 4 numbers per block
        winner = blocks.argmax(axis=4)                       # which of the 4 was biggest
        self.mask = np.arange(4) == winner[..., None]        # True at the winner only
        return blocks.max(axis=4)

    def backward(self, d):
        N, C, H, W = self.in_shape
        Ho, Wo = H // 2, W // 2
        blocks = self.mask * d[..., None]                    # all blame to the winner, 0 to the rest
        blocks = blocks.reshape(N, C, Ho, Wo, 2, 2).transpose(0, 1, 2, 4, 3, 5)
        dx = np.zeros(self.in_shape, d.dtype)
        dx[:, :, :2 * Ho, :2 * Wo] = blocks.reshape(N, C, 2 * Ho, 2 * Wo)
        return dx

The forward pass uses a reshape trick instead of a loop. Take a 4 x 4 map. Reshaping it to (2, 2, 2, 2) splits the rows into 2 groups of 2 and the columns into 2 groups of 2. The transpose brings the two "group" axes next to each other and the two "inside the block" axes to the end. A last reshape joins the inside axes, so each 2 x 2 block becomes a row of 4 numbers. Then max(axis=4) takes the biggest of each block, for the whole batch in one call.

argmax gives the position (0 to 3) of the biggest number in each block. The line np.arange(4) == winner[..., None] turns that position into the mask: four True/False values per block, True only at the winner. I use argmax and not "equal to the maximum" on purpose. If two numbers in a block tie, which happens often after ReLU when a whole block is 0, "equal to the maximum" would mark both and send the blame twice. argmax picks exactly one winner.

The backward pass multiplies the mask by the incoming blame, which puts each block's blame at its winner and zeros elsewhere. Then it undoes the reshape steps in reverse order to get back to the input layout. If the input had an odd last row or column that pooling dropped (the 29 x 29 map), those pixels keep a blame of 0, because they never reached the output.

Flatten and Dense

class Flatten:
    """Unroll (N, C, H, W) into (N, C*H*W). No maths, only a new shape."""

    def forward(self, x):
        self.in_shape = x.shape
        return x.reshape(x.shape[0], -1)

    def backward(self, d):
        return d.reshape(self.in_shape)


class Dense:
    """Fully connected layer: every input is joined to every output."""

    def __init__(self, n_in, n_out, rng=None, dtype=np.float32):
        rng = rng or np.random.default_rng(0)
        self.W = (rng.standard_normal((n_in, n_out)) * np.sqrt(2.0 / n_in)).astype(dtype)
        self.b = np.zeros(n_out, dtype)

    def forward(self, x):
        self.x = x
        return x @ self.W + self.b

    def backward(self, d):
        self.dW = self.x.T @ d          # (n_in, n_out)
        self.db = d.sum(axis=0)
        return d @ self.W.T             # blame for the inputs

Flatten only changes the shape and remembers the old one. reshape(x.shape[0], -1) means "keep the batch axis, and work out the second size yourself", which gives (N, 1152).

In Dense, x @ self.W is matrix multiplication: for each picture, each of the 64 outputs is the sum of all 1,152 inputs times their weights. The backward lines are the table row from chapter 8. self.x.T @ d gives a gradient for every weight: input value times output blame, added up over the batch. d @ self.W.T passes the blame back to the inputs through the same weights.

Softmax and loss_and_grad

def softmax(z):
    """Turn each row of scores into chances that are positive and add up to 1."""
    z = z - z.max(axis=1, keepdims=True)        # does not change the answer, avoids huge exp()
    e = np.exp(z)
    return e / e.sum(axis=1, keepdims=True)


def loss_and_grad(scores, y):
    """Cross-entropy loss of a batch, and its gradient with respect to the scores.

    scores : (N, 12) raw outputs of the last layer
    y      : (N,) the right class index of each picture
    Returns (loss, d) where d has the shape of scores and feeds Net.backward.
    """
    N = scores.shape[0]
    p = softmax(scores)
    loss = -np.mean(np.log(p[np.arange(N), y] + 1e-12))
    d = p.copy()
    d[np.arange(N), y] -= 1.0                   # chances minus the one-hot answer
    return float(loss), d / N

Softmax first subtracts each row's largest score from the whole row. This does not change the chances, because the same factor cancels in the top and bottom of the fraction. But it makes the largest exponent e0 = 1, so np.exp can never overflow, whatever the scores are.

In loss_and_grad, p[np.arange(N), y] picks, for each picture, the chance given to its right class. The loss is the average of minus the logarithm of those chances. The tiny 1e-12 protects against the logarithm of exactly 0. The gradient is the result from chapter 8: the chances, with 1 subtracted at the right class, divided by N because the loss is an average over the batch.

Why are softmax and the loss in one function?

Separately, the gradient of the loss with respect to the chances and the gradient of softmax with respect to the scores are both awkward, and dividing by a chance near zero is numerically risky. Together they collapse into "chances minus the one-hot answer", which is simple and safe. So the network's last layer outputs raw scores, and this one function does softmax, loss and gradient in one place.

The Net class: forward, backward, step

def __init__(self, seed=0, dtype=np.float32):
    rng = np.random.default_rng(seed)
    self.layers = [
        Conv(3, 8, rng=rng, dtype=dtype, need_dx=False), ReLU(), MaxPool(),   # -> 8 x 31 x 31
        Conv(8, 16, rng=rng, dtype=dtype), ReLU(), MaxPool(),                 # -> 16 x 14 x 14
        Conv(16, 32, rng=rng, dtype=dtype), ReLU(), MaxPool(),                # -> 32 x 6 x 6
        Flatten(),                                                            # -> 1,152
        Dense(32 * 6 * 6, 64, rng=rng, dtype=dtype), ReLU(),                  # -> 64
        Dense(64, len(CLASSES), rng=rng, dtype=dtype),                        # -> 12 scores
    ]
    # The layers that own weights, with the names used in weights.npz.
    idx = [0, 3, 6, 10, 12]
    names = ["conv1", "conv2", "conv3", "dense1", "dense2"]
    self.named = [(n, self.layers[i]) for n, i in zip(names, idx)]
    # One "velocity" array per weight array, for momentum.
    self.velocity = {(n, p): np.zeros_like(getattr(layer, p))
                     for n, layer in self.named for p in ("W", "b")}

def forward(self, x):
    for layer in self.layers:
        x = layer.forward(x)
    return x                                 # (N, 12) scores, softmax NOT applied yet

def backward(self, d):
    for layer in reversed(self.layers):
        d = layer.backward(d)

def step(self, lr=0.01, momentum=0.9):
    """One SGD-with-momentum update of every weight, using the stored gradients."""
    for name, layer in self.named:
        for p in ("W", "b"):
            w = getattr(layer, p)                        # the weight array itself
            v = self.velocity[(name, p)]                 # its velocity array
            v *= momentum                                # keep 90% of the old direction
            v -= lr * getattr(layer, "d" + p)            # add a step downhill
            w += v                                       # move the weights, in place

The constructor builds the list of 13 layers in order, with the shapes of chapter 7 in the comments. One random number generator rng, started from a fixed seed, fills all the starting weights. A fixed seed means the same "random" weights every run, so a training run can be repeated exactly. self.named lists the five layers that own weights, with their names. self.velocity holds one zero-filled array per weight array for momentum.

forward passes x through every layer. backward passes d through every layer in reverse order. They are three lines each because every layer follows the same pattern.

step is the momentum update from chapter 8, applied to all 10 weight arrays. The operators *=, -= and += change the arrays in place, which means the numbers inside the existing arrays are overwritten and no new arrays are created. That keeps the layer and the network pointing at the same weights, and saves memory.

One training step, as used in train.py, is then four lines:

scores = net.forward(x_batch)               # pictures -> scores
loss, d = loss_and_grad(scores, y_batch)    # how wrong, and the first blame message
net.backward(d)                             # blame back through every layer
net.step(lr=0.01, momentum=0.9)             # move every weight a small step

Saving and loading the weights

def get_weights(self):
    """A dictionary of copies of the 10 weight arrays."""
    return {f"{n}_{p}": getattr(layer, p).copy() for n, layer in self.named for p in ("W", "b")}

def set_weights(self, arrays):
    for n, layer in self.named:
        for p in ("W", "b"):
            a = arrays[f"{n}_{p}"]
            if a.shape != getattr(layer, p).shape:
                raise ValueError(f"{n}_{p}: file has {a.shape}, network needs {getattr(layer, p).shape}")
            setattr(layer, p, a.astype(getattr(layer, p).dtype))

def save_weights(self, path):
    np.savez(path, **self.get_weights())

def load_weights(self, path):
    with np.load(path) as data:
        self.set_weights({k: data[k] for k in data.files})

A trained network is nothing but its weights. get_weights collects the 10 arrays into a dictionary with names such as conv1_W and dense2_b. np.savez writes them into one file, weights.npz. load_weights reads the file back and set_weights copies each array into its layer, after checking that the shape matches. If I ever change the network and try to load an old file, the check stops with a clear message instead of letting a wrong shape cause a confusing error later.

The training script also uses get_weights on its own: after each epoch with a new best validation accuracy, it takes a copy of the weights in memory, and at the end it saves that best copy.

Predicting

def predict(net, x):
    """Class index and confidence (0..1) for ONE prepared picture x of shape (1, 3, 64, 64)."""
    p = softmax(net.forward(x))[0]
    best = int(p.argmax())
    return best, float(p[best])


def top_k(net, x, k=3):
    """The k most likely classes for one picture, best first: [(class_index, chance), ...]."""
    p = softmax(net.forward(x))[0]
    order = np.argsort(p)[::-1][:k]
    return [(int(i), float(p[i])) for i in order]

predict is what the kiosk calls. It runs the forward pass, applies softmax, and returns the index of the highest chance together with that chance. top_k returns the best three, which the app shows when the customer taps "Wrong item" or when the confidence is below 0.60. np.argsort gives the positions that would sort the chances from small to large; [::-1] reverses that to large first.

Why float32

NumPy's default decimal type is float64: 8 bytes, about 16 significant digits. All weights and pictures in my network are float32: 4 bytes, about 7 digits.

  • Half the memory. Arrays are half as large, so more of them fit in the processor's fast cache memory.
  • Faster arithmetic. The Pi's processor can multiply four float32 numbers in one instruction but only two float64 numbers. On the Pi this is a large part of the difference between a quick and a slow forward pass.
  • Enough precision. The input pixels have only 256 levels each. Seven digits of precision are far more than the data contains.

The one place I use float64 is the gradient check, where I need to see differences in the seventh digit and beyond. The dtype argument of Net exists for exactly that.

Be careful

NumPy silently turns a result into float64 if any float64 array takes part in the calculation. One careless np.zeros(shape) without a dtype in the middle of the network would make everything after it float64 and half as fast, with no error message. That is why every array I create copies its type from an existing one: np.zeros(..., x.dtype) or np.zeros_like(x). A quick check is net.forward(x).dtype, which must print float32.

The gradient check code

The check from chapter 8 is a short script, gradient_check.py. Its core is this function:

def relative_difference(net, x, y, weights, pos, analytic, eps):
    """Nudge one weight up and down by eps and compare the measured slope with mine."""
    old = weights[pos]
    weights[pos] = old + eps
    up = loss_of(net, x, y)
    weights[pos] = old - eps
    down = loss_of(net, x, y)
    weights[pos] = old                                   # put it back
    numeric = (up - down) / (2 * eps)                    # central difference
    return abs(numeric - analytic) / max(1e-12, abs(numeric) + abs(analytic))

It changes one weight up and down by eps, computes the loss each time with the forward pass only, and puts the weight back. The measured slope is compared with analytic, the gradient my backward pass stored for that weight. The main part of the script builds the real Net in float64, runs one forward and backward pass on four random pictures, and calls this function for 20 random weights in each of the 10 arrays. A weight that differs by more than 1e-5 is measured once more with a 10 times smaller nudge, to rule out the kinks of ReLU and max pooling. The script prints the worst difference per array and ends with PASS or FAIL.

Why check the real network and not each layer alone?

Checking the whole network end to end tests every layer and also the way the layers are joined: the order of the backward calls, the reshape in Flatten, the dropped row in the odd-sized pooling. A layer can be right alone and still be wired wrongly. Because conv1's weights sit at the very start, their gradient passes through every other layer's backward code, so a pass for conv1 is a pass for the whole chain.

Interview tip

I practise saying the two hardest backward rules without looking. Conv: "Forward, I loop over the nine filter cells; each adds the shifted input times that cell's weights. Backward, the same loop: the weight gradient is the incoming gradient times the shifted input, summed over batch and positions; the input gradient adds the incoming gradient times the weights back into the same shifted block." Pool: "Forward keeps the maximum of each 2 x 2 block and remembers which one won. Backward sends the gradient only to the winner." If I can say these two, I can rebuild the rest.
