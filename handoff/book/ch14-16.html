14 Price, bill and the touchscreen app

Short version: prices come from a small CSV file. Every price is worked out and added in whole paise, never in decimal rupees, so the total is always exact. The app is a Tkinter window that runs a short function, the tick, 10 times a second. The tick reads the scale once and moves the app through five states: Waiting, Settling, Identifying, Showing and Remove. The weight starts the camera, and a "Wrong item" button lets the customer fix the 7 in 100 items the network gets wrong.

The price table: prices.csv

The price of each item, in rupees per kilogram, lives in a plain text file, kiosk/prices.csv. CSV means comma-separated values: one line per row, with commas between the columns. Any spreadsheet program can open and edit it.

The prices are the ones from version 1's price file, without Capsicum and Chilly. The function load_prices reads the file into a Python dictionary, so prices["Tomato"] gives 35. At start-up, check_prices makes sure every one of the 12 classes has a price. If one is missing, the app stops at once with a clear message, instead of crashing later in front of a customer.

def load_prices(path):
    """Read prices.csv into a dictionary {"Tomato": 35, ...} of whole rupees per kg."""
    prices = {}
    with open(path, newline="", encoding="utf-8") as f:
        for row in csv.DictReader(f):
            prices[row["item"].strip()] = int(row["rupees_per_kg"])
    return prices


def check_prices(prices, class_names):
    """Stop at start-up if any class the network knows has no price."""
    missing = [name for name in class_names if name not in prices]
    if missing:
        raise ValueError(f"prices.csv has no price for: {', '.join(missing)}")
Why a file and not prices in the code?

Prices change every week in a vegetable shop. The person who changes them should not need to edit Python. With a CSV file, a shopkeeper can change "35" to "40" in any text editor or spreadsheet, and the kiosk uses the new price after a restart. It also keeps the code the same in every shop: only the price file differs.

Prices are whole rupees per kilogram. That matches how produce is priced in Indian shops, and it keeps every later calculation in whole numbers.

Money in paise, and why

A paisa is one hundredth of a rupee. Instead of storing "Rs 14.42", the kiosk stores the whole number 1,442. Every price is calculated in paise, every sum is a sum of paise, and the only time rupees appear is when a number is printed on the screen.

The float trap

Computers store decimal numbers such as 8.78 as floats: binary fractions with a fixed number of digits. Most decimal fractions cannot be written exactly in binary, just as 1/3 cannot be written exactly in decimal (0.3333...). So 8.78 is stored as a number extremely close to 8.78, but not equal to it. The tiny errors are invisible one at a time, and then show up when numbers are added:

>>> 0.1 + 0.2
0.30000000000000004
>>> 8.78 + 6.3                 # a beetroot and an onion
15.079999999999998
>>> 14.42 + 12.15 + 31.2       # three bill lines
57.769999999999996

Printed with two decimals, 15.079999999999998 still shows as 15.08, so the bug hides. But comparisons fail ("is the total equal to 15.08?" says no), and in a long day of bills rounding each line in different places can make the till disagree with the bills by a paisa here and there. In accounting, a total that is off by one paisa is a wrong total.

Why whole paise fix it

Whole numbers are stored exactly. 878 + 630 is exactly 1,508, every time, on every computer. By turning each line into whole paise once, at the moment it is priced, and adding only whole numbers from then on, the total can never drift. This is how banks and payment systems handle money too: in the smallest unit, as whole numbers.

The price formula

A price per kilogram times a weight in grams, in paise, is:

paise = grams x rupees_per_kg x 100 / 1000

412 g of tomato at Rs 35/kg:   412 x 35 x 100 / 1000 = 1,442 paise = Rs 14.42

The "x 100" turns rupees into paise and the "/ 1000" turns kilograms into grams. The weight is first rounded to whole grams, because the bill shows whole grams and should charge exactly what it shows. The result can still end in half a paisa (for example 1,033 g of onion at Rs 25/kg is 2,582.5 paise), so the function rounds that half up.

def price_paise(grams, rupees_per_kg):
    """Price of `grams` (rounded to whole grams) at `rupees_per_kg`, in whole paise.

    paise = grams x rupees_per_kg x 100 / 1000, rounded half up. All whole numbers.
    """
    g = int(round(grams))                     # the bill shows and charges whole grams
    return (g * rupees_per_kg * 100 + 500) // 1000


def rupees(paise):
    """1442 -> 'Rs 14.42'. Paise become rupees only when they are shown."""
    return "Rs " + money(paise)

Adding 500 before dividing by 1,000 with // (whole-number division, which drops the remainder) is a classic way to round half up using only whole numbers. rupees prints paise as rupees by splitting them into paise // 100 rupees and paise % 100 paise (% gives the remainder), so even printing never touches a float.

Be careful

Python's own round() rounds an exact half to the nearest even number: round(2582.5) gives 2582 but round(2583.5) gives 2584. This "banker's rounding" is fair on average, but it surprises customers who learned "half rounds up" at school. My price function does not use round() for paise; it uses the add-500 trick so a half paisa always rounds up.

The Bill class

The bill is a list of lines. Each line holds the name, the whole grams, the rupees per kilogram and the price in paise.

class Bill:
    """The customer's bill: a list of lines and a total, all in paise."""

    def __init__(self):
        self.lines = []                       # each line: (name, grams, rupees_per_kg, paise)

    def add(self, name, grams, rupees_per_kg):
        line = (name, int(round(grams)), rupees_per_kg, price_paise(grams, rupees_per_kg))
        self.lines.append(line)
        return line

    def remove_last(self):
        if self.lines:
            self.lines.pop()

    def clear(self):
        self.lines = []

    @property
    def total_paise(self):
        return sum(line[3] for line in self.lines)

    def text(self):
        """The bill as lines of text, the same layout the screen shows."""
        rows = [f"{'Item':<14}{'Grams':>7}{'Rs/kg':>7}{'Rs':>9}"]
        for name, g, rpk, p in self.lines:
            rows.append(f"{name:<14}{g:>7}{rpk:>7}{money(p):>9}")
        rows.append("-" * 37)
        rows.append(f"{'Total':<28}{money(self.total_paise):>9}")
        return "\n".join(rows)

total_paise is a property that adds up the last column. It is worked out fresh every time it is read, so it can never disagree with the lines. text() lays the bill out in fixed-width columns. Running python3 bill.py checks the small examples at the top of the file and prints a sample bill:

Design story

Version 1 calculated each cost as grams * price * 0.001, rounded it to two decimals, and added the costs as floats. It usually looked right because every number was printed with two decimals. The paise design came from asking a simple question: "can the total ever be off by a paisa?" With floats the honest answer was "rarely, but yes". With whole paise it is "never".

The state loop

The app is always in exactly one state, and each state has its own screen and its own rules for what happens next. This design is called a state machine. It turns a messy question ("what should the app do when the weight changes?") into small, separate questions ("what should the Settling state do when the weight changes?").

Why the weight starts the camera

The weight is the trigger for everything. The kiosk never asks "is there something in the camera's view?"; it asks "has the weight gone up and stayed still?". There are four reasons.

  1. The right moment. A steady weight means the item is down, has stopped rolling, and the hand has left. That is exactly when a photo shows the item clearly and alone.
  2. One photo per item. The CNN runs once per item instead of 30 times a second, which keeps the Pi cool and idle between customers.
  3. No false triggers. A hand waving over the tray, a shadow or a dropped receipt changes the picture but not the weight (or not by 20 g).
  4. The weight is needed anyway. The price needs a steady weight, so waiting for it costs nothing extra.

Why "Wrong item" exists

The network is right 92.6% of the time on test crops. That means about 7 in every 100 items would be named wrongly if the app simply trusted it. Two features handle this. Below a top chance of 0.60, the app does not guess at all: it shows "Not sure, please choose" with the top 3 guesses. Above 0.60, it shows its answer but always with a "Wrong item" button next to "Add to bill". Both lead to the same Choose screen: the top 3 guesses as big buttons, which for a mosambi nearly always includes Lemon, and "Other items" for the full list of 12.

Why not just make the network better?

Even a much better network would make some mistakes, and a mistake on a bill costs real money and trust. The honest design accepts that the model is sometimes wrong and makes the correction cheap: one tap, with the right answer usually already on screen. In my 60-item kiosk test, the right item was in the top 3 for 5 of the 6 wrong first answers. A human in the loop for 7% of items is a good trade for a kiosk that handles the other 93% alone.

Be careful

The "Wrong item" button also lets a dishonest customer choose a cheaper item on purpose: weigh pomegranates, tap "Wrong item", pick Onion. My kiosk trusts the customer, like many self-checkouts. A shop version would log every correction with its photo for a staff member to check (chapter 20).

Tkinter in plain words

Tkinter is the window toolkit that comes with Python. It draws windows, text labels and buttons, and it tells my program when a button is pressed. On the Pi it comes from the python3-tk package.

A Tkinter program works differently from a script that runs top to bottom. After building the window, the program calls root.mainloop() and hands control to Tkinter. The main loop waits for events (a tap, a key, a timer), runs the small function connected to each event, redraws the screen, and waits again. My code never runs "in the background": it only runs inside these short functions, called by the main loop.

The weight, though, changes without any event. To check the scale regularly, I ask Tkinter for a timer event: root.after(100, tick) means "in 100 ms, call tick". At the end of every tick, the tick asks for the next one. So the tick runs 10 times a second, forever, and between ticks Tkinter is free to handle taps and redraw the screen.

def tick(self):
    """Runs every 100 ms: one scale reading, one filter update, one state step."""
    try:
        raw = self.scale.read_raw(timeout=0) if self.scale.is_ready() else None
        self.no_reading = 0 if raw is not None else self.no_reading + 1
        grams = self.filter.add(raw)
        self.status.config(text="Scale not responding" if self.no_reading > NO_READING_LIMIT else self.note)
        self.step(grams)
    except Exception:
        traceback.print_exc()                    # keep the kiosk alive; the log shows what happened
    finally:
        self.root.after(TICK_MS, self.tick)

Each tick checks whether the HX711 has a reading waiting (is_ready()), reads it if so, feeds it to the filter and calls step, which is the state machine of Figure 14.1. The finally block makes sure the next tick is always booked, even if something in this tick fails, and the except prints the error to the log without stopping the kiosk.

def step(self, grams):
    s, f = self.state, self.filter
    if s == WAITING:
        if grams > self.on_g:
            self.go(SETTLING)
    elif s == SETTLING:
        self.big.config(text=f"{grams:.0f} g")   # live weight
        if grams < self.off_g:
            self.go(WAITING)                     # it was lifted off again
        elif f.steady and f.weight < self.on_g:
            self.go(WAITING)                     # steady but under 20 g: not an item
        elif f.steady:
            self.identify()
    elif s in (SHOWING, CHOOSING):
        if grams < self.off_g:
            self.go(WAITING)                     # taken off without adding: nothing is billed
        elif f.steady and abs(f.weight - self.item["grams"]) > CHANGED_G:
            self.go(SETTLING)                    # something was added or swapped: weigh again
    elif s == REMOVE:
        if grams < self.off_g:
            self.go(WAITING)

The classic mistake: while True

The natural first idea for reading a scale forever is a loop:

while True:                      # DO NOT do this in a Tkinter app
    grams = filter.add(scale.read_raw())
    label.config(text=f"{grams:.0f} g")

In a Tkinter app this freezes the window completely. The loop never returns to the main loop, so Tkinter never gets a chance to draw the new text or notice a tap. The screen shows whatever was there when the loop started, and buttons do nothing. The fix is exactly the tick: do one small piece of work, return, and ask to be called again.

Why does the CNN run inside the tick?

While the tick runs, the screen cannot react, so long work inside a tick is normally avoided. The photo and the CNN take about 60 ms once per item, and the screen is about to change anyway. A 60 ms pause is shorter than a blink. Moving the CNN to a separate thread would add locks and shared-state problems for no visible gain.

Identifying, in code

def identify(self):
    """One photo, one prediction. Called once per item, when the weight is steady."""
    self.state = IDENTIFYING
    guesses = None
    photo = self.camera.take_photo()
    box = camera.find_item_box(photo) if photo is not None else None
    if box is not None:
        x = prepare_image(crop_with_margin(photo, box))
        guesses = top_k(self.net, x, 3)
    else:
        self.note = "Could not see the item, please choose"
    self.item = {"grams": self.filter.weight, "guesses": guesses}
    if guesses and guesses[0][1] >= self.threshold:
        self.go(SHOWING)
    else:
        self.go(CHOOSING)

This is the only place the camera and the network are used. If the photo fails or the colour mask finds nothing, there are no guesses, and the Choose screen opens with the full list and a message. The customer can always finish the purchase, even if the camera is covered.

Fullscreen, 800 x 480, big buttons

The app fills the whole 7-inch screen with attributes("-fullscreen", True), and hides the mouse pointer, which has no use on a touchscreen. There is no title bar, no desktop and no way for a customer to reach another program. The layout has three parts: a teal bar at the top with the item count and the running total, a large middle area for the current screen, and a thin status line at the bottom for messages such as "Scale not responding".

Why big buttons and no typing?

A fingertip covers about 1 cm of screen. On a 7-inch screen with 800 x 480 pixels, 1 cm is about 50 pixels, so every button is at least 2 cm tall with large bold text and a gap around it. Typing on a small touchscreen keyboard is slow and error-prone, so the kiosk never asks for text: every choice is a button, and the item list has only 12 names.

Finish and New customer

When the customer has put down their last item, they tap "Finish" on the Waiting screen. The Bill screen shows every line with name, grams, rupees per kilogram and rupees, then the total, in the same fixed-width layout as Bill.text(). While the bill is shown, the app ignores the scale, so leaning on the tray cannot start a new item.

"Back" returns to Waiting with the bill kept, for a customer who forgot an item. "New customer" clears the bill and returns to Waiting for the next person. In this version, payment happens at the shop's counter or by the shop's own UPI code; the kiosk's job ends with a correct, itemised total.

Interview tip

Two short answers prepare most app questions. "How does the UI stay responsive while reading a sensor?" "Tkinter's main loop calls a tick every 100 ms with root.after; each tick reads the scale once and returns, so the UI never blocks. A while-True loop would freeze it." And "Why paise?" "Floats can't store 8.78 exactly, so sums drift: 8.78 + 6.3 gives 15.079999999999998. Whole paise are exact, so the total is always exactly the sum of the lines."

Start-up order

The app does its slow and risky work once, before the first screen, in a fixed order:

The tick, step by step

Every 100 ms, Tkinter calls the tick. One tick does this:

  1. Ask the HX711 if a reading is waiting. If yes, read it (about 0.4 ms). If no, use None.
  2. Count ticks without a reading. After 30 in a row (3 s), show "Scale not responding".
  3. Feed the reading to the filter and get the cleaned grams. The filter also re-tares by itself if the tray has been empty and steady for 5 s.
  4. Run one step of the state machine with the cleaned grams. In Settling this updates the live weight; when the weight becomes steady it runs identify() once, which takes the photo and runs the CNN.
  5. Book the next tick in 100 ms, whatever happened above.

Button presses happen between ticks. Tkinter calls the button's function, which changes the state and draws the new screen, and the next tick continues from the new state.

Why check is_ready() instead of waiting for a reading?

read_raw() can wait up to 100 ms for the HX711 to finish a reading. Waiting inside the tick would freeze the screen for that time, 10 times a second. Checking is_ready() first means the tick never waits: if a reading is there, take it; if not, try again next tick. Both the HX711 and the tick run at about 10 per second, so almost every tick finds a fresh reading.

At start-up nobody is waiting and nothing has been billed, so a missing file is best reported loudly and at once. During a sale, a customer is standing there with items half scanned. Testing the pieces alone

Most of the kiosk can be tested on a laptop, with no Pi, no camera and no scale:

  • The filter: python3 weight_filter.py checks its doctest and replays a made-up run with a wild reading (chapter 13).
  • The bill: python3 bill.py checks the paise examples, including rounding half up, and prints a sample bill.
  • The network: python3 cnn_numpy.py checks the fast convolution against the slow one; gradient_check.py checks every backward pass; saved test crops check the accuracy.
  • The camera's box finder: find_item_box runs on any saved photo of the tray.
  • The whole app: python3 kiosk_app.py --simulate --windowed (below).

Only HX711.read_raw and Camera.take_photo truly need the hardware, and they are the two smallest pieces of code in the kiosk.

The simulated-scale flag

python3 kiosk_app.py --simulate --windowed runs the full app in an 800 x 480 window on a laptop. --simulate swaps in two stand-ins: SimulatedHX711, which behaves like my real scale (offset 123,450, 431 counts per gram, a little noise, an occasional wild reading), and FakeCamera, which draws a blue tray with a coloured round "item". The keys 1 to 9, 0, Q and W put one of the 12 items on the pretend tray with a typical weight, and the space bar takes it off.

On a laptop without RPi.GPIO, hx711.py still imports, because a small stand-in object with the same function names replaces the missing library. That is what lets the app, and the book's tests, run anywhere.

This is a real test I ran, not a prediction. With --simulate, I put a 412 g tomato down, added it, took it off, then put a 1,033 g onion down and chose it on the "Not sure" screen, and tapped "Finish". The app passed through Waiting, Settling, Showing, Remove, Waiting, Choose and Bill in that order, and the bill showed Tomato Rs 14.42, Onion Rs 25.83, total Rs 40.25.

Be careful

The simulated run tests the app's logic, not the network: the fake camera draws coloured circles, which the CNN has never seen, so its guesses in a demo are meaningless. To demo recognition on a laptop, I use saved real photos instead.

Autostart with systemd

Chapter 5 showed the service file. In terms of program structure, systemd is the outermost layer: it starts kiosk_app.py after the desktop, restarts it 3 s after any crash, and collects everything the app prints into a log I can read over SSH with journalctl --user -u kiosk.service. That log is where the tracebacks from the tick's error handler end up.

Interview tip

"How is your code structured?" My answer: "One module per job: CNN, HX711, filter, camera, bill, and an app that wires them together. Only two small functions need hardware, so I test everything else on a laptop, and the app has a simulate flag with a fake scale and camera. At run time it's a Tkinter main loop with a 100 ms tick driving a state machine, no threads, and systemd restarts it if it ever crashes."

Design story

Version 1 was one 360-line file with the GUI, the HTTP request to the ESP8266, the YOLOv5 call and the price maths mixed together, and Windows paths typed into it. Testing any part meant running the whole thing with the hardware connected. Splitting version 2 into small files was what made it possible to write most of the code and the tests before the Pi was even wired.

16 Power, frame and the physical build

Short version: one 5 V 3 A supply powers the whole kiosk, which draws about 1.1 A. The MDF box from version 1 holds everything: a post carries the camera 35 cm above the tray, an LED strip beside it lights the tray, the tray rests only on the load cell, and the touchscreen stands at a slant at the front with the Pi screwed to its back. Cables are routed so that nothing touches the tray.

Power: one supply for everything

The official Raspberry Pi 5 V 3 A USB-C supply is the only power input. From the Pi, power spreads to every other part.

Measured value (predicted, replace with your own number after your test)

With a USB-C power meter between the supply and the Pi, the whole kiosk drew about 1.1 A at 5.1 V while showing "Place an item" with the LED strip on, and briefly about 1.3 A during the photo and CNN step. The supply voltage never dropped below 5.0 V, and the lightning symbol never appeared.

Why a 3 A supply when the kiosk uses 1.1 A?

The Pi 4 can draw much more for short moments: at start-up, when all four cores are busy, or when a USB device switches on. A supply that is just big enough lets the voltage sag at those moments, which shows as the lightning symbol, a slowed processor, or a camera that disconnects. The official 3 A supply also keeps its voltage slightly above 5 V on purpose, to make up for the loss in the cable. Spare capacity is cheap insurance.

Be careful

The 5 V pin on the header is joined directly to the supply, with no fuse between them and the screen. A short circuit on the screen's power wires goes straight to the supply. I use the screen's own jumper wires, push them fully onto the pins, and never plug or unplug them with the power on.

Heat

The Pi's processor slows itself down if it gets too hot (it starts at 80 °C). The kiosk is idle most of the time and runs the CNN for 18 ms per item, so heat is not a real problem, but the Pi sits in a closed box behind a screen. The stick-on heat sinks and a few holes drilled in the MDF behind the screen keep it comfortable.

Measured value (predicted, replace with your own number after your test)

Read with vcgencmd measure_temp, the processor was at about 52 °C after start-up and about 58 °C after an hour of use with a customer every minute, far below the 80 °C where it would slow down.

The camera height and the light

The camera is fixed to a short arm at the top of a vertical post at the back of the box. The arm holds the camera over the centre of the tray, lens pointing straight down, 35 cm above the tray surface. At that height the C270 sees about 29 cm x 22 cm, which covers the 25 cm x 20 cm tray with a small border.

The 30 cm LED strip is stuck along the underside of the same arm, beside the camera, so its light falls straight down on the tray. Light from directly above makes only small shadows, right under each item, which keeps the colour mask's box tight.

Why put the light right beside the camera?

Light from the side throws long shadows across the tray. A shadow is not blue, so the colour mask would count it as part of the item and make the box too big. Light from the camera's own direction hides each item's shadow mostly underneath the item itself. It also makes the brightness of every photo nearly the same, which is the reason the LED strip exists (chapter 3).

The frame from version 1

The frame is the MDF box my team built for version 1. I reused it unchanged except for three things: a mount for the touchscreen, holes for cables and air, and a new shelf for the HX711.

Why mount the Pi on the back of the screen?

The official 7-inch display has four threaded standoffs on its back made exactly for a Pi. Mounting it there keeps the short DSI ribbon and the two power jumpers short and protected, needs no extra box, and puts the Pi close to the HX711 on the base, so the four signal wires stay at 20 cm. It also puts the warmest part of the kiosk behind the screen, where the air holes are.

Why lean the screen back?

A customer standing at a counter looks down at about 45 degrees. A screen standing upright would be seen at a sharp angle, with reflections from ceiling lights. Leaning it back about 30 degrees faces it towards the customer's eyes and makes the large buttons easy to tap without reaching over the tray.

The tray rests only on the load cell

Chapter 4 gave the rule; here is how the build follows it. The load cell is screwed down at one end through a 10 mm spacer, with two M5 screws into the base. The tray is screwed at its centre to the other end through a second spacer, with two M4 screws. The spacers give the bar room to bend. Around the tray there is a gap of at least 5 mm to the post, the screen and the edge of the box.

Be careful

The screws holding the tray must be the right length. A screw that goes too deep into the load cell presses on the bending part and changes its behaviour; a loose screw lets the tray rock, which the steady rule then never accepts. I tightened them firmly, then checked that the empty scale settled to within 1 g of zero after tapping the tray.

Cable routing

Every cable has a fixed path so that none can rest on the tray or pull on the screen.

  • Camera USB and LED strip USB run down the back of the post, held by cable clips every 10 cm, then along the base behind the tray to the Pi.
  • Load cell leads leave the cell on the fixed end, which does not move, and run along the base to the HX711. A lead fixed to the moving end would carry some of the tray's weight.
  • HX711 to Pi jumpers rise from the base to the Pi's header behind the screen, bundled with a cable tie.
  • The power cable enters through a hole at the back of the base, with a cable tie inside as strain relief, so a pull on the cable cannot reach the Pi's USB-C socket.
Measured value (predicted, replace with your own number after your test)

Before I clipped the camera cable to the post, it hung down behind the tray and touched its back edge. A 500 g check weight then read 470 g, and the error changed each time the cable moved. With the cable clipped, the reading went back to 499.2 g.

The order I assembled it in

The order of assembly mattered, because some parts are hard to reach once others are in place.

  1. Load cell first. I screwed the fixed end to the base through its spacer and checked with a ruler that the bar was level and its arrow pointed down. Everything about the scale depends on this one joint being solid.
  2. HX711 next, before the tray. With the tray off, the load cell's four leads are easy to route along the base and screw into the HX711's terminals. I ran hx711.py at this point and pressed the bare bar with a finger to see the numbers rise.
  3. Tray. Fixed to the free end through the second spacer, then checked for the 5 mm gap all round by sliding a folded card around its edge.
  4. Camera and light. Clamped the camera to the arm, stuck the LED strip beside it, clipped both cables down the post. I looked at a test photo to centre the tray in the picture before tightening the clamp.
  5. Screen and Pi last. The Pi goes onto the back of the screen with the ribbon and the two power jumpers, then the screen onto its slanted mount, then the four HX711 jumpers and the two USB plugs.
  6. Calibrate only after everything is fixed. Any change to the tray, the screws or the cables can shift the zero or the slope, so calibrate.py is the very last step.
Why test each part as it goes in?

A fault found right after fitting a part has one possible cause: that part. The same fault found when the whole kiosk is closed up could be any of ten things, and reaching the load cell means taking the tray off again. Running hx711.py with the tray off, then with the tray on, then camera.py, took five minutes in total and meant that when the app first ran on the finished kiosk, it worked.

What I would build differently

Three things about the physical build are fine for a prototype and wrong for a shop. MDF swells if it gets wet, and a vegetable counter gets wet; a product would use plastic or coated metal. The jumper wires on the header can be knocked loose; a product would use a small soldered board or a screw-terminal HAT. And the tray has no cover against wind or a leaning elbow; a real scale has a guard so that only the item can touch the weighing surface. None of these change how the kiosk works, but each one is a way a real shop would break it within a week.

The finished kiosk, from the customer's side

A customer sees a blue tray in front of them, a small camera and light above it, and a touchscreen to the left saying "Place an item". There are no wires on show, no keyboard and no buttons other than those on the screen. The whole kiosk stands on a counter, needs one wall socket, and needs no network to work.

Interview tip

Physical questions are often about trade-offs I can show I thought about. Two good ones: "Why does the light sit next to the camera?" (shadows fall under the items, so the colour mask's boxes stay tight) and "What did you learn from the build?" (a single cable touching the tray made the scale read 30 g light; in a weighing device, mechanics matter as much as code).

Design story

Version 1's frame held a camera over a tray and a separate ESP8266 board, and the laptop stood beside it. Version 2 kept the box and the camera post, removed the ESP8266, and brought the computer inside the kiosk by mounting the Pi behind the touchscreen. The kiosk went from "a box plus a laptop plus a phone hotspot" to one object with one plug.
